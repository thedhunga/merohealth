# PWA installability — verification notes

Round seven, task R, first bullet. Verified 2026-08-18 against a production
build (`pnpm build && pnpm start`) served at `http://localhost:3000`.

## Method

This session has no physical Android or iOS device and no WebKit/Safari
engine available (only Chromium is installed). So "verify install" here
means the closest thing a headless agent can do honestly:

- **Chrome DevTools Protocol `Page.getInstallabilityErrors`** — the actual
  signal Chrome uses internally to decide whether to show the install
  mini-infobar / `beforeinstallprompt`. This is not a reimplementation of
  Chrome's heuristic; it *is* Chrome's heuristic, read via CDP against a
  real (non-incognito — `launchPersistentContext`, since an ephemeral
  `chromium.launch()` context always reports `in-incognito` and tells you
  nothing) Chromium profile.
- **`Page.getAppManifest`** for Chrome's own manifest parse errors.
- Direct fetch of each icon route with `file` to confirm real PNG bytes at
  the declared dimensions, and a fetch of the rendered `<head>` for the
  Apple-specific tags Chrome's manifest check doesn't cover.
- A 375×812 screenshot, since every UI-adjacent check in this repo is
  measured at phone width, not assumed.

**What this does not cover:** an actual phone. Nobody tapped "Install" on
an Android handset or "Add to Home Screen" on an iPhone and looked at the
result. If someone has five minutes with a phone, that spot-check is still
worth doing — nothing below should be read as a substitute for it, only as
the strongest evidence a headless run can produce.

## Findings — Android Chrome

**Installable, no errors.** `Page.getInstallabilityErrors` returned
`{ "installabilityErrors": [] }` on `/` in a real (non-incognito) Chromium
profile. `Page.getAppManifest` returned zero parse errors. Concretely:

- `manifest.webmanifest` serves with valid JSON, `display: "standalone"`,
  `start_url`, `name`/`short_name`, and `theme_color`/`background_color` —
  everything the mini-infobar check requires.
- `/icon-192.png`, `/icon-512.png`, `/icon-maskable-512.png` all resolve
  (`200`, `content-type: image/png`) and decode to exactly the declared
  pixel dimensions (192×192, 512×512, 512×512) — checked with `file`, not
  just trusted from the route name.
- No service worker exists yet (`/sw.js` and `/service-worker.js` both
  404) — Round seven task R's second bullet is still open. Chrome's install
  signal did not require one; a fetch-handling service worker is still the
  right thing to add for the offline page in the next bullet, just not a
  blocker for the prompt itself.
- Splash screen and standalone chrome are generated by Chrome from the same
  manifest fields (icon, `background_color`, `name`) already verified above
  — there's no separate asset to check.

## Findings — iOS Safari

**Correctly tagged for standalone launch, one caveat.** The rendered
`<head>` on `/` carries:

- `<link rel="apple-touch-icon" ... sizes="180x180">` — resolves, decodes to
  180×180 (`apps/web/src/app/apple-icon.tsx`).
- `<meta name="apple-mobile-web-app-title" content="मेरो स्वास्थ्य">`
- `<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">`
- `<meta name="mobile-web-app-capable" content="yes">` — the modern,
  standard tag. **Not present:** the legacy `apple-mobile-web-app-capable`
  tag. Next.js 16.3's metadata API (`appleWebApp.capable`) only emits the
  standard tag now (confirmed in `next/dist/lib/metadata/metadata.js`);
  there's no supported `Metadata` field to add the legacy one back short of
  a raw `<meta>` in the document head.
  - Apple added support for the standard tag in Safari 17.4 (March 2024).
    By August 2026 that's over two years of OS updates, so in practice this
    should be a non-issue on any iOS device someone is actually installing
    to today. Recorded here rather than "fixed" because it's Next's
    considered default, not a bug in this repo, and adding the legacy tag
    back would mean fighting the framework for a pre-2024 iOS version this
    product has no evidence anyone is still running.
- `viewport-fit=cover` is set (`layout.tsx`'s `viewport` export), so a
  standalone-launched app paints under the notch/home indicator instead of
  leaving black bars — the actual "no Safari chrome" requirement.

## Screens measured at 375×812 (first-time-visitor layout, no history)

`document.body.scrollHeight` 1627px / `innerHeight` 812px → **2.00 screens**,
inside the Round seven O budget ("under 2.5 phone screens total").

## What the next run should know

- If task R's second bullet (service worker) lands, re-run the CDP
  installability check afterward — a service worker with a bad fetch
  handler is a way to accidentally regress a currently-clean installability
  verdict.
- A real phone spot-check (Android: does the mini-infobar/install prompt
  actually appear and produce a standalone window with the right icon and
  splash? iOS: does Add to Home Screen produce a chrome-free launch?) is
  still open and cheap — worth doing whenever anyone on the team has a
  phone in hand, not worth blocking this task on.
